# 代码规范（Code Style Guide）

| 项目 | 内容 |
|------|------|
| 文档版本 | v1.0 |
| 适用范围 | 神人社团小程序（前端 `miniprogram/` + 云函数 `cloudfunctions/`） |
| 技术栈 | JavaScript / 微信小程序原生 / 微信云开发 |
| 生效日期 | 2026-09-04 |
| 制定依据 | 参考 Google JavaScript Style Guide、Airbnb Style Guide、阿里巴巴 Java 开发手册 |

---

## 1. 引言与核心原则

本规范是本项目的技术契约，用于统一代码风格、降低协作成本、提升可维护性。所有提交必须符合本规范，代码审查以本规范为唯一判定依据。

规范遵循三条基本原则，优先级由高到低：

1. **一致性优先**：与现有代码保持一致，优于「绝对正确」。若局部风格与本规范冲突，以文件内既有一致风格为准，但不得跨文件混用。
2. **可读性优于性能**：任何以可读性为代价的性能优化，必须附有可复现的测量数据作为依据。
3. **规范是契约而非口号**：每条规则应可被执行、可被审查，避免「建议性」的模糊表述。

规则分级约定：

- **【强制】**：必须遵守，违反即判定审查不通过。
- **【推荐】**：应当遵守，特殊情况可豁免但需说明理由。
- **【参考】**：建议参考，不作强制要求。

## 2. 命名规范

### 2.1 变量与函数【强制】

- 使用**小驼峰（lowerCamelCase）**命名。
- 变量用名词或名词短语，函数用动词或动词短语，做到「见名知义」。
- 禁止使用无意义的缩写与单字母变量（循环计数器 `i`、`j`、`k` 除外）。

```js
// 正例
const userAccount = fetchUserAccount()
const totalItems = calculateTotal()

// 反例
const cnt = getData()   // cnt 语义不明
let d                    // 单字母且非循环变量
```

### 2.2 常量【强制】

- 使用**全大写 + 下划线（UPPER_SNAKE_CASE）**命名。
- 所有魔法数字必须提取为具名常量，禁止散落在逻辑中。

```js
// 正例
const MAX_RETRY_COUNT = 3
const PAGE_TRANSITION_DURATION = 200

// 反例
if (retry > 3) { ... }      // 魔法数字 3
```

### 2.3 布尔值【强制】

- 使用 `is` / `has` / `can` 前缀，使语义一目了然。

```js
// 正例
const isSignedUp = true
const hasMore = false
const canSubmit = true

// 反例
const signedUp = true   // 语义模糊，无法直接读出布尔类型
```

### 2.4 集合与数据库命名【强制】

- 云数据库集合、云函数名、页面路径一律使用**小驼峰**（多词）或**单小写词**，禁止下划线、连字符、大驼峰。

```js
// 正例
getActivityList、activity_comments、pages/admin/mascot-manage（历史遗留，新代码禁止连字符）

// 反例
get_activity_list、GetActivityList
```

### 2.5 命名词典【参考】

项目内高频术语统一约定，避免同一概念多种叫法：

| 概念 | 统一用词 | 禁止替代 |
|------|---------|---------|
| 用户 | user | customer / member |
| 活动 | activity | event / campaign |
| 报名 | signup | register / enroll |
| 新闻/公告 | news | article / post |
| 草案 | draft | proposal（与 `proposal` 页面路径区分） |
| 吉祥物 | mascot | character / figure |
| 社费 | fund | fee / budget |
| 云函数返回 | `{ code, msg, data }` | 无 |

## 3. 代码风格

### 3.1 缩进与换行【强制】

- 统一使用 **2 空格**缩进，禁止 Tab 与 4 空格混用（`project.config.json` 中 `tabSize: 2`）。
- 单行代码长度建议不超过 100 字符，超长时按语义换行。
- 文件末尾保留一个空行，禁止多余连续空行（不超过 2 行）。

### 3.2 分号【强制】

- 本项目采用**无分号风格**，依赖自动分号插入（ASI）。
- 例外：`for` 循环头部的小括号内分号必须保留。

```js
// 正例
const app = getApp()
this.setData({ loading: true })

for (let i = 0; i < total; i++) {   // for 头部分号保留
  console.log(i)
}

// 反例
const app = getApp();
```

### 3.3 引号【强制】

- 字符串一律使用**单引号**，模板字符串使用**反引号**。
- 对象键名不加引号，除非包含非法字符。

```js
// 正例
const name = '活动'
const url = `/pages/detail/index?id=${id}`
const data = { title, pageSize: 20 }

// 反例
const name = "活动"
```

### 3.4 括号与空格【强制】

- 控制语句关键字与左括号之间保留一个空格；函数调用名与左括号之间不留空格。
- 二元运算符两侧保留一个空格；逗号后保留一个空格。

```js
// 正例
if (condition) { ... }
function handleTap() { ... }
const sum = a + b
fetchData(page, pageSize)

// 反例
if(condition){ ... }
function handleTap (){ ... }
```

### 3.5 对象与数组【强制】

- 优先使用字面量与解构、展开运算符，保持简洁。

```js
// 正例
const { title, cover } = activity
const list = [...oldList, ...newItems]

// 反例
const title = activity.title
const cover = activity.cover
```

## 4. 注释规范

### 4.1 注释原则【强制】

- 注释解释「为什么」，而非复述「做什么」。
- 复杂逻辑（正则、算法、状态机、事务、缓存策略）必须注释设计意图。

```js
// 正例：解释设计意图
// 采用乒乓播放（正序到尾后反向），避免循环首尾跳变突兀
currentFrame += direction

// 反例：无意义复述
// 自增 currentFrame
currentFrame += direction
```

### 4.2 JSDoc 注释【强制】

- 每个**文件**必须包含模块级头注释：说明职责、依赖、关键约定。
- 每个**云函数**的 `exports.main` 必须包含 JSDoc：入参说明（`@param`）与返回结构（`@returns`）。
- 每个**非平凡函数**（含业务逻辑、跨模块调用、复杂算法）应包含 JSDoc。

```js
/**
 * 用户登录
 *
 * 入参说明：
 * @param 无
 * @returns {Object} 统一返回 { code, msg, data }，code 为 0 表示成功
 */
exports.main = async (event, context) => { ... }
```

### 4.3 行内注释【强制】

- 使用 `//` 单行注释，与代码之间保留一个空格。
- 禁止使用 `/* */` 作行内注释；块注释仅用于文件头与 JSDoc。

```js
// 正例
const ratio = 0.5625   // 动画帧原始宽高比（720 / 1280）

// 反例
const ratio = 0.5625 /* 宽高比 */
```

### 4.4 禁用冗余注释【强制】

- 不注释显而易见的事实（如 `i++ // 自增`）。
- 不保留被注释掉的死代码；无用代码应直接删除，由版本控制追溯。

## 5. 函数与模块设计

### 5.1 单一职责【强制】

- 一个函数只做一件事；一个页面只负责一个业务域；一个云函数只暴露一个操作。

### 5.2 函数长度与参数【推荐】

- 单个函数长度不超过 50 行，超过则按职责拆分。
- 参数数量不超过 3 个，超过时应封装为对象。

```js
// 正例
function createUser(userInfo) { ... }   // 单参数对象

// 反例
function createUser(name, studentId, phone, role, extra) { ... }
```

### 5.3 纯函数优先【推荐】

- 无副作用、仅依赖入参的函数优先编写，便于测试与复用。
- 涉及 `this`、全局状态、异步副作用的函数，应明确标注职责边界。

### 5.4 避免魔法数字【强制】

- 所有有语义的数值必须具名化，见 2.2。

## 6. 错误处理

### 6.1 统一返回协议【强制】

- 云函数返回值统一为 `{ code, msg, data }`，`code === 0` 表示成功，非 0 为错误码。
- 错误码约定如下：

| 错误码 | 含义 |
|--------|------|
| 0 | 成功 |
| 400 | 参数错误 |
| 401 | 未登录 / 无法获取用户身份 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 500 | 服务端异常 |

### 6.2 云函数异常处理【强制】

- 业务校验失败直接返回对应错误码；`try/catch` 捕获预期外异常并返回 `500`，同时 `console.error` 记录现场。

```js
// 正例
try {
  const res = await db.collection('activities').doc(id).get()
  if (!res.data) return { code: 404, msg: '活动不存在' }
  return { code: 0, data: res.data }
} catch (e) {
  console.error('getActivityDetail error:', e)
  return { code: 500, msg: '获取活动详情失败' }
}
```

### 6.3 前端错误处理【强制】

- 所有 `wx.cloud.callFunction` 必须有 `catch` 分支，并给出用户可理解的提示（`wx.showToast`）。
- 禁止静默吞异常；至少输出 `console.error`。

## 7. 云函数规范

### 7.1 目录结构【强制】

- 每个云函数独立目录，包含 `index.js`（入口）、`package.json`（依赖）、`config.json`（权限配置）。
- 函数名与目录名一致，命名见 2.4。

### 7.2 权限校验【强制】

- 涉及管理操作（增删改）的云函数，必须在校验 `OPENID` 后，查询 `users` 集合确认 `role === 1`，否则返回 `403`。
- 权限校验必须置于业务逻辑之前。

```js
// 正例：先鉴权，再业务
const userRes = await db.collection('users').where({ _openid: OPENID }).get()
if (userRes.data.length === 0 || userRes.data[0].role !== 1) {
  return { code: 403, msg: '无权限操作' }
}
```

### 7.3 数据库操作【强制】

- 查询尽量使用 `where` 条件过滤，避免全量 `get` 后在内存中过滤。
- 涉及多集合一致性（如报名人数增减）必须使用**事务**。

```js
// 正例：事务保证一致性
const transaction = await db.startTransaction()
try {
  await transaction.collection('signups').add({ data: { ... } })
  await transaction.collection('activities').doc(id).update({ data: { currentParticipants: _.inc(1) } })
  await transaction.commit()
} catch (e) {
  await transaction.rollback()
  return { code: 500, msg: '操作失败' }
}
```

### 7.4 依赖管理【强制】

- 仅声明实际使用的依赖，禁止引入未调用的包（遗留的 `sharp` 等需清理）。

## 8. 小程序页面规范

### 8.1 Page 结构【强制】

- 页面统一使用 `Page({ data, onLoad, ... })` 结构。
- `data` 中仅存放与视图渲染相关的状态，非渲染变量挂载在 `this` 上（如 `this.canvas`、`this.ctx`）。

### 8.2 setData【强制】

- 避免频繁、大对象 `setData`；多次更新合并为一次。
- 禁止在 `setData` 后立即读取 `this.data` 期望得到最新值（`setData` 是异步的）。

```js
// 正例：合并为一次 setData
this.setData({ list, loading: false, hasMore })

// 反例
this.setData({ list })
this.setData({ loading: false })
```

### 8.3 导航统一封装【强制】

- 页面跳转、返回、Tab 切换一律通过 `app` 统一封装方法（`app.navigateTo` / `app.navigateBack` / `app.switchTab` / `app.reLaunch`），禁止直接调用 `wx.*`，以保证切换动画一致。

```js
// 正例
app.navigateTo({ url: `/pages/activity/detail/index?id=${id}` })

// 反例
wx.navigateTo({ url: `/pages/activity/detail/index?id=${id}` })
```

### 8.4 图片加载【推荐】

- 列表类 `<image>` 标签应添加 `lazy-load`，减少首屏非必要请求。

## 9. 性能规范

1. **图片**：列表缩略图启用懒加载；上传前压缩（项目已统一用 Canvas 压缩出原图 + 缩略图）。
2. **背景图**：云存储临时链接通过统一 `app.getBgUrl` 获取，加载失败走本地兜底图，避免白屏。
3. **缓存**：高频静态资源（如欢迎页动画帧）应落地缓存并设置过期时间。
4. **循环**：避免在循环体内进行网络请求或大对象序列化。
5. **渲染**：减少不必要的 `setData` 与深层节点渲染（见 8.2）。

## 10. 安全规范

1. **鉴权后置**：所有权限判断在云函数侧完成，前端仅做体验层拦截，不作为安全边界。
2. **参数校验**：云函数对入参做完整性、类型、格式校验（如 `fileID` 需以 `cloud://` 开头）。
3. **用户数据隔离**：查询「我的」数据必须以 `OPENID` 为条件，禁止根据前端传入的用户标识查询他人数据。
4. **敏感信息**：云环境 ID 等配置集中管理，禁止在页面代码中散落硬编码（历史硬编码需逐步收敛为常量）。

## 11. Git 提交规范

提交信息遵循 `type: description` 格式，type 取值如下：

| type | 用途 |
|------|------|
| `feat` | 新增功能 |
| `fix` | 修复缺陷 |
| `refactor` | 重构（不改变外部行为） |
| `style` | 样式调整（不影响逻辑） |
| `perf` | 性能优化 |
| `docs` | 文档更新 |
| `chore` | 构建、依赖、杂项 |

规则：

- **【强制】** 描述使用祈使句、小写开头，简洁说明「做了什么」。
- **【强制】** 一次提交只做一类事，避免功能与重构混杂。
- **【推荐】** 描述采用中文，如 `feat: 添加吉祥物管理功能`。

```bash
# 正例
feat: 添加吉祥物管理功能
fix: 修复活动报名人数统计偏差

# 反例
update code
改了点什么
```

## 12. 代码审查清单（Checklist）

审查时逐项核对，全部通过方可合并：

- [ ] 命名符合第 2 节约定，无语义不明变量
- [ ] 无魔法数字，常量已具名化
- [ ] 无分号风格一致，for 头部除外
- [ ] 引号统一为单引号，无混用
- [ ] 文件头 / 云函数 JSDoc 齐全
- [ ] 注释解释「为什么」，无冗余注释与死代码
- [ ] 云函数返回统一 `{ code, msg, data }`，错误码正确
- [ ] 管理操作有权限校验
- [ ] 多集合一致性使用事务
- [ ] 前端异步调用有 `catch`，无静默吞异常
- [ ] 页面导航走统一封装，无 `wx.*` 直调
- [ ] 列表图片已懒加载，上传图片已压缩
- [ ] 无 emoji 与装饰符号（颜文字除外）
- [ ] 提交信息符合第 11 节格式
